預約系統 + 多客戶測驗系統整合第一階段：功能盤點報告
日期：2026-08-27

一、整合目標

目標不是單純把兩份程式碼合併，而是把「預約系統」升級成一套可獨立交付給客戶的完整漏斗系統。

整合後系統應包含：
1. 預約系統：仿 Calendly 的預約、排班、顧問、Calendar / Meet / Gmail、自動提醒。
2. 測驗系統：測驗型漏斗、題目管理、分數/分類、檢測報告、測驗作答 CRM、測驗後跟進信。
3. 共用 CRM：同一個客戶 Lead 需同時看得到基本資料、測驗作答、分數結果、預約狀態、顧問歸屬、信件紀錄、CRM 備註。
4. 可獨立交付：可複製成客戶自己的 GitHub / Vercel / Supabase / Google OAuth 系統。

四、兩套系統重複功能與合併判斷

1. 客戶 / 租戶隔離
- 預約系統：tenant_slug + Supabase，較適合作為正式 SaaS / 獨立交付基底。
- 測驗系統：client_id + Google Sheets，概念正確但效能與維護性較弱。
- 合併策略：保留預約系統 Supabase 架構，吸收測驗系統 client_id 模型為 tenant/project/version。

2. CRM
- 預約系統 CRM 強在預約流程、顧問操作、改期取消轉派。
- 測驗系統 CRM 強在作答資料、分數、報告、測驗狀態。
- 合併策略：建立 unified leads / crm_records，讓同一客戶同時有 quiz_response 與 appointment。

3. 表單 / 題目
- 預約系統目前表單偏諮詢前篩選。
- 測驗系統題目是完整測驗漏斗，有版本、階段、分數、結果報告。
- 合併策略：分成「預約表單」與「測驗題目」兩個模組，但底層可共用 question/options 結構。

4. 信件
- 預約系統信件編輯器較新，有 HTML editor、圖片、退訂、重試。
- 測驗系統信件目的更完整，包含測驗完成與測驗跟進。
- 合併策略：保留預約系統 email_templates / email_queue，新增 trigger：quiz_completed、quiz_followup、quiz_completed_unbooked。

5. 預約
- 預約系統已比測驗系統更完整，應作為主體。
- 測驗系統的預約前篩選、從 rid 帶入資料、報告頁 CTA 需要搬入。

6. 後台 UI
- 預約系統視覺較符合目前方向。
- 測驗系統左側 nav 較符合功能量變大後的操作方式。
- 合併策略：使用預約系統的視覺語言，改成測驗系統式左側收合導航。

六、建議整合策略

採用「預約系統升級」路線：
1. 保留現有 Vercel / Supabase / GitHub 架構。
2. 把測驗系統的資料模型和功能逐步搬進 Supabase。
3. 把 admin.html 從上方 tabs 改為左側收合導航。
4. 先整合資料模型，再搬 UI。
5. 完成後產出客戶獨立交付包。

不建議直接把 GAS 測驗系統整包貼進目前專案，原因：
1. GAS / Sheets 架構與目前 Supabase 架構不同。
2. 直接混合會造成兩套登入、兩套 CRM、兩套 Email queue。
3. 後續做客戶獨立交付會更難維護。

八、關於客戶獨立交付 B 方案

正確理解如下：
1. 先在目前你的帳號 / repo 中把整合版做完。
2. 完工並測試穩定後，把它整理成可複製交付包。
3. 客戶若要獨立擁有，就用客戶自己的帳號建立：
   - GitHub repo
   - Vercel project
   - Supabase project
   - Google Cloud OAuth project
4. 再把同一套程式碼 copy / fork / import 到客戶帳號。
5. 重新設定客戶自己的 env、OAuth redirect URI、資料庫 schema、初始管理員。
6. 後續若要更新客戶獨立版，需要用版本同步或人工 merge，不會像 SaaS A 方案那樣自動所有客戶一起更新。

結論：
整合應以「預約系統」作為正式技術基底，將「測驗系統」的漏斗、作答、分數、報告、測驗 CRM 和跟進信功能移植進來。完成後再做 B 方案的客戶獨立複製流程。
