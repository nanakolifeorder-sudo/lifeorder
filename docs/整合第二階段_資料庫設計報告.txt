預約系統 + 多客戶測驗系統整合第二階段：資料庫設計報告
日期：2026-08-27

一、第二階段目標

本階段只做資料庫與資料模型設計，不直接大改 UI。

整合原則：
1. 以目前「預約系統升級版」的 Supabase / Postgres 架構作為正式技術基底。
2. 保留既有預約、排班、顧問、CRM 操作、改期、取消、轉派、自選改期與提醒信管理。
3. 將「待整 - 多客戶測驗系統」的測驗漏斗、題目版本、題目階段、作答、分數、報告內容、測驗跟進信整合進同一套 Supabase 資料模型。
4. 預約表單與測驗題目在 UI 與資料語意上分開。
5. 多客戶 / tenant 底層保留，但客戶版 UI 預設隱藏多客戶管理；工程師 / 最高權限後台入口等到實作入口時再向使用者確認網址命名。


二、現有 Supabase schema 盤點

目前主要 schema 來源：
- sql/schema.sql
- sql/upgrade-security-email-backup.sql
- sql/upgrade-booking-base-urls.sql

目前後端主要使用：
- lib/db.js：使用 node-postgres pg Pool 透過 DATABASE_URL 直連 Postgres。
- lib/service.js：集中處理租戶、預約、顧問、CRM、Email queue、OAuth 等業務流程。
- lib/auth.js：登入與權限判斷，目前帳號資料仍放在 consultants 表。

目前沒有看到 Supabase client / RLS policy 實作，權限隔離主要由後端 query 的 tenant_slug 條件與 JWT session 控制。第二階段設計先維持這個模式，避免一次同時改 auth / RLS / UI，之後可以另開安全強化階段補 RLS。

現有資料表：

1. tenants
- 主鍵：slug
- 用途：租戶 / 客戶底層隔離。
- 重要欄位：name、owner_name、owner_email、owner_password_hash、app_base_url、booking_base_urls、webhook_secret、created_at。
- 整合判斷：保留。未來工程師 / 最高權限後台仍以 tenants 作為跨客戶管理入口。

2. projects
- 主鍵：id
- 唯一鍵：(tenant_slug, code)
- 用途：租戶底下的專案 / 漏斗。
- 重要欄位：code、name、status、main_url、fallback_url、booking_notice、reject_type、reject_value。
- 整合判斷：保留並擴充。測驗版本、測驗頁、報告頁、iframe 安裝碼、預設版本都應掛在 project 層級。

3. consultants
- 主鍵：id
- 唯一鍵：(tenant_slug, login_email)
- 用途：顧問資料、登入帳號、權限、Google / Microsoft OAuth token、行事曆與會議工具設定。
- 重要欄位：calendar_id、google_email、google_refresh_token、microsoft_email、microsoft_refresh_token、permissions、project_codes、meet_tool、time_zone、interval_minutes、buffer_before、buffer_after、min_days、max_days。
- 整合判斷：保留。測驗系統的使用者管理 UI 不搬，但底層帳號 / 權限仍沿用 consultants。

4. availability_rules
- 主鍵：id
- 用途：顧問 weekly / specific 可預約時段。
- 整合判斷：保留。測驗系統的一對一排班不搬。

5. questions
- 主鍵：id
- 用途：目前的預約前表單題目。
- 重要欄位：project_code、sort_order、title、type、options jsonb、reject_word、is_required。
- 整合判斷：保留為「預約表單」。不改名以降低既有功能風險，但文件與 UI 命名要明確稱為 booking_form_questions 或 預約表單題目。

6. appointments
- 主鍵：id
- 用途：預約紀錄。
- 重要欄位：project_code、consultant_id、event_id、meet_link、start_at、end_at、client_name、client_email、client_phone、answers、status、attendance、deal_status、plan、notes。
- 重要索引：uq_active_appointment_slot，避免同租戶同顧問同時間重複有效預約。
- 整合判斷：保留並擴充 lead_id / crm_contact_id / quiz_response_id，使報告頁預約能回連到測驗作答。

7. rejected_clients
- 主鍵：id
- 用途：預約前表單淘汰 / 婉拒名單。
- 整合判斷：保留，短期繼續支援既有 UI；中期應匯入 CRM 統一資料模型與 timeline。

8. waitlist_clients
- 主鍵：id
- 用途：無可預約時段或未能直接預約者。
- 整合判斷：保留，短期支援既有等候名單與發送時段選擇；中期應回寫 CRM 統一資料模型與 timeline。

9. page_views
- 主鍵：id
- 用途：預約頁瀏覽統計。
- 整合判斷：保留，可擴充 page_type 以支援 quiz / report / booking 分頁瀏覽。

10. email_templates
- 主鍵：id
- 用途：信件模板。
- 重要欄位：project_code、name、trigger_name、time_param、subject、body、status、sender_name、stop_when_booked。
- 現有 trigger：lead_created、booking_created、booking_rescheduled、reschedule_link、meeting_before、meeting_after、booking_cancelled，以及程式中已預留 rejected_created、waitlist_created。
- 整合判斷：保留並擴充 trigger 類型、purpose/module 與 delay unit。UI 上拆成「提醒信管理」與「跟進信管理」，底層仍共用同表。

11. leads
- 主鍵：id
- 唯一鍵：(tenant_slug, project_code, client_email)
- 用途：目前的未預約名單 / CRM 名單追蹤。
- 重要欄位：client_name、client_email、client_phone、answers、status、booked_appointment_id。
- 整合判斷：擴充成 CRM 統一主表的短期基底，但不建議再把所有測驗作答 JSON 塞進 answers。測驗應有 quiz_responses / quiz_response_answers；leads 只放人的最新狀態與最近關聯。

12. email_queue
- 主鍵：id
- 用途：寄信佇列。
- 重要欄位：lead_id、appointment_id、template_id、trigger_name、client_name、client_email、subject、body、scheduled_at、sent_at、cancelled_at、status、retry_count、max_attempts、last_attempt_at。
- 現有寄送邏輯：runDueEmails 抓 queued + scheduled_at <= now()，claim 成 sending，檢查退訂，若 stop_when_booked 且 trigger_name = lead_created，查 appointments 有有效預約則取消。
- 整合判斷：保留並擴充 quiz_response_id / crm_event_id / purpose，stop_when_booked 需支援 quiz_followup 類觸發。

13. email_suppressions
- 主鍵：id
- 唯一鍵：(tenant_slug, client_email)
- 用途：退訂 / 拒收名單。
- 整合判斷：保留。

14. admin_alerts
- 主鍵：id
- 用途：系統告警。
- 整合判斷：保留。測驗跟進信、報告生成、分數規則錯誤可寫入告警。

15. login_attempts
- 主鍵：id
- 用途：登入暴力防護。
- 整合判斷：保留。

用途：

6. quiz_score_ranges

用途：
- 定義每個分數面向的分數區間與對應報告內容。

建議欄位：
- id bigserial primary key
- tenant_slug text not null references tenants(slug) on delete cascade
- project_code text not null
- version_code text not null
- dimension_key text not null
- range_key text not null
- label text not null default ''
- min_score numeric(10,2) not null
- max_score numeric(10,2) not null
- title text not null default ''
- subtitle text default ''
- body text default ''
- image_url text default ''
- cta_label text default ''
- cta_url text default ''
- sort_order integer not null default 0
- status text not null default '啟用'
- created_at timestamptz not null default now()
- updated_at timestamptz not null default now()

必要限制：
- check (min_score <= max_score)
- 同一 tenant_slug + project_code + version_code + dimension_key 下，啟用區間不可重疊。

Postgres 不重疊建議做法：
- 啟用 btree_gist extension。
- 使用 numrange(min_score, max_score, '[]') exclusion constraint。
- 或若暫時避免 extension，先在後端儲存時 transaction 內檢查 overlap。

建議 constraint：
create extension if not exists btree_gist;

alter table quiz_score_ranges
  add constraint quiz_score_ranges_no_overlap
  exclude using gist (
    tenant_slug with =,
    project_code with =,
    version_code with =,
    dimension_key with =,
    numrange(min_score, max_score, '[]') with &&
  )
  where (status <> '停用');

注意：
- 如果業務希望 0-5 與 5-10 可共用邊界，需改成 '[)' 並明確規定上限不含。依目前使用者描述「0-5、6-10」，建議採整數分數與閉區間，後端檢查 5 和 6 不重疊。

- 將同一租戶、同一專案、同一 Email 的人統一成一張客戶資料卡。

建議欄位：
- id bigserial primary key
- tenant_slug text not null references tenants(slug) on delete cascade
- project_code text not null
- name text not null default ''
- email text not null
- phone text default ''
- status text not null default 'active'

- created_at timestamptz not null default now()

lifecycle_stage 建議值：

五、CRM 統一資料模型

建議採「crm_contacts 主檔 + 關聯事件/紀錄表」。

1. crm_contacts 是客戶資料卡入口

查詢一位客戶時：
- 基本資料：crm_contacts
- 測驗紀錄：quiz_responses where crm_contact_id = ?
- 作答詳情：quiz_response_answers where quiz_response_id in (...)
- 多面向分數：quiz_responses.score_summary
- 報告結果：quiz_responses.report_snapshot + quiz_score_ranges
- 預約紀錄：appointments where crm_contact_id = ? 或同 tenant/project/email fallback
- 顧問歸屬：crm_contacts.assigned_consultant_id + appointments.consultant_id
- Email 發送歷程：email_queue where crm_contact_id = ? 或 crm_timeline_events event_type like email_%
- 備註 / 狀態：crm_contacts.notes/status/lifecycle_stage + crm_timeline_events
- 操作按鈕：仍呼叫既有預約 action，但 payload 帶 crm_contact_id / quiz_response_id

2. leads 的定位

短期：
- leads 繼續支援既有 trackLead / systemeWebhook / email follow-up。
- 新增測驗提交時，同步 upsert leads，避免現有 Email 與 CRM 畫面斷掉。

中期：
- CRM 主畫面改讀 crm_contacts。
- leads 可變成「行銷名單狀態」或逐步降級為相容表。

3. 同一客戶的合併規則

主要合併鍵：
- tenant_slug + project_code + lower(email)

補充：
- phone 可作為人工合併提示，不建議自動用電話合併，避免共用電話或格式問題。
- 同 email 可在不同 project 各自存在，符合多專案 / 多漏斗隔離。
- 同一 project 可有多次 quiz_responses，但 crm_contacts.latest_quiz_response_id 指向最近一次。

4. 客戶 CRM 首頁統計

今天多少人作答：
- count(*) from quiz_responses
- where tenant_slug = ? and submitted_at >= today_start and submitted_at < tomorrow_start

今天多少人預約：
- count(*) from appointments
- where tenant_slug = ? and created_at >= today_start and created_at < tomorrow_start

未預約名單：
- crm_contacts where lifecycle_stage in ('lead', 'quiz_completed', 'unbooked')
- 或 latest_quiz_response_id is not null and latest_appointment_id is null

即將到來行程：
- appointments where start_at >= now() and status not in cancelled statuses

主介面名單清單：
- 以 crm_contacts 為主表，left join latest quiz / latest appointment 摘要。


六、Email trigger / queue 支援測驗跟進

1. 底層共用

保留：
- email_templates
- email_queue
- email_suppressions
- runDueEmails
- Gmail sender：目前 getSenderConsultant 會找 tenant admin / owner 的 Google refresh token，符合「系統信件使用使用者管理員 Gmail」方向。

擴充：
- email_templates.module = quiz
- email_queue.module = quiz
- email_queue.quiz_response_id
- email_queue.crm_contact_id
- email_queue.cancellation_policy

2. 測驗完成流程

submitQuiz 建議流程：
1. 驗證 tenant/project/version/status。
2. upsert crm_contacts。
3. insert quiz_responses。
4. insert quiz_response_answers。
5. 計算 score_summary。
6. 建立 report_snapshot。
7. update crm_contacts.latest_quiz_response_id、lifecycle_stage = quiz_completed 或 unbooked。
8. upsert leads，status = pending 或 quiz_completed。
9. insert crm_timeline_events event_type = quiz_completed。
10. queueTriggeredEmails(trigger = quiz_completed)。
11. queueTriggeredEmails(trigger = quiz_followup / quiz_completed_unbooked)，且 cancellation_policy = stop_when_booked。

3. 預約完成後停止未預約跟進

submitBooking 建議新增：
1. 若 payload 帶 quizResponseId / resultId，查 quiz_responses.public_id。
2. appointment 寫入 quiz_response_id、crm_contact_id、lead_id。
3. update quiz_responses.appointment_id。
4. update crm_contacts.latest_appointment_id、lifecycle_stage = booked。
5. update leads.status = booked。
6. cancelQueuedFollowups：
   - 同 tenant_slug
   - 同 project_code
   - 同 lower(client_email)
   - status = queued
   - cancellation_policy = stop_when_booked 或 stop_when_booked = true
   - module in ('quiz', 'booking')，但 booking 的 meeting_before / meeting_after 不應取消
7. insert crm_timeline_events event_type = booking_created。

4. runDueEmails 調整方向

目前邏輯只在 item.stop_when_booked && trigger_name === 'lead_created' 時檢查已預約。

建議改為：
- 若 item.stop_when_booked = true 或 item.cancellation_policy = 'stop_when_booked'：
  - 查 appointments 中同 tenant/project/email 有 status 非取消的有效預約。
  - 若有，取消該 queue。
- 寄送成功後：
  - update email_queue status = sent。
  - insert crm_timeline_events event_type = email_sent。
- 寄送失敗後：
  - retry 或 failed。
  - insert crm_timeline_events event_type = email_failed。

5. Email 變數擴充

現有變數：
- name / email / phone / project / time / meetLink / consultant / rescheduleLink / unsubscribeLink

測驗新增建議：
- quizResultUrl
- reportUrl
- scoreSummary
- topDimension
- topDimensionName
- bookingUrl
- latestScore.{dimension_key}
- rangeTitle.{dimension_key}

實作時不建議一開始做任意深層模板語法。MVP 可先支援固定變數與 scoreSummary 文字。


七、報告編輯器區塊資料模型

核心資料表：
- quiz_result_settings：報告整體設定。
- quiz_score_dimensions：分數面向。
- quiz_score_ranges：分數區間與區間內容。
- quiz_report_blocks：報告頁區塊。
- quiz_responses.report_snapshot：作答當下報告快照。

1. 編輯器儲存方式

後台編輯一個版本的報告頁時：
- quiz_result_settings 存全局設定。
- quiz_report_blocks 存區塊列表。
- 區塊上移 / 下移只更新 sort_order。
- 區塊顯示 / 隱藏只更新 is_visible。
- 區塊刪除可硬刪，或 status = deleted。建議 MVP 硬刪即可，正式版可改軟刪。

2. 分數區間內容

使用者要求：
- 不採低 / 中 / 高固定門檻。
- 每個面向可設定多個不重疊分數區間。
- 每個分數區間內容可設定文案與圖片。
- 區間區塊可新增、刪除、排序。

建議：
- quiz_score_ranges 負責區間與內容。
- quiz_report_blocks 的 score_range_content 區塊負責在報告頁某個位置渲染「目前作答命中的區間內容」。
- 若要在同一報告放多個面向的診斷，建立多個 score_range_content block，各自指定 dimension_key。

3. 預覽

預覽資料不需要另建表。

後台預覽可用：
- mode = desktop / mobile 僅為前端狀態。
- preview_score_summary 由前端暫存，或後端提供 sample response。

若後續需要保存範例，可新增：
- quiz_report_preview_samples

第二階段 MVP 不必新增。

4. 報告快照策略

quiz_responses.report_snapshot 建議包含：
- version_code
- score_summary
- matched_ranges
- rendered_blocks 或 matched_content
- generated_at

原因：
- 客戶測完後收到信件連結，若管理員之後修改報告區間，舊客戶不應默默看到完全不同診斷。
- 若業務希望所有舊結果套用新文案，可提供「重新產生報告」操作。

十一、風險與待確認事項

1. 分數區間邊界規則
- 建議採整數閉區間，例如 0-5、6-10。
- 若未來有小數分數，需明確規定 max 是否包含。技術上建議使用半開區間 [min, max)，但對一般使用者較不直覺。

2. 舊報告是否固定快照
- 建議預設固定快照。
- 若要讓舊結果套用新版報告，需要額外「重新產生報告」功能。

3. leads 是否最終保留
- 建議短期保留，避免影響 email queue 與既有 CRM。
- 中期可以讓 crm_contacts 成為主資料模型，leads 成為相容層。

4. RLS / Supabase Auth
- 目前是 Node pg 直連 DATABASE_URL，非 Supabase Auth + RLS。
- 第二階段先不改，避免擴大風險。
- 正式商用多租戶若要強化資料隔離，應另開安全階段設計 RLS 或後端 service role 邊界。

5. Zoom 欄位
- 目前 consultants.meet_tool 可放工具名稱，但 Zoom OAuth / 固定 Zoom 連結欄位尚未完整正式化。
- 第二階段資料模型可先讓 appointments.meeting_tool / meeting_url 支援 Zoom 連結，但 Zoom API 串接可晚於測驗資料模型。
